/goal
Make FunnySharp workflows practical with domain-specific values, explicit state variants and typed error composition so consumers can exclude meaningful invalid combinations without maintaining a parallel collection of parsing and error-adaptation boilerplate. Completion means an executable business workflow distinguishes otherwise confusable identifiers, constructs a constrained value through a validated boundary, permits operations only on their appropriate domain state where C# can enforce that distinction, and preserves the source-specific information in errors composed across modules. Demonstrate the improvement against ordinary records, interfaces, pattern matching and manually written adapters, including all type declarations and conversions rather than counting only the final chain. Clearly separate facts enforced by the compiler, checks performed at construction or decoding, and conditions still dependent on storage, authorization or concurrency. Default struct values, null references, mutable payloads, deserialization and alternative construction paths must not invalidate the published guarantee; a state-specific value must not be advertised as proof that a database row is unchanged or an operation ran exactly once. Completion evidence consists of representative compiling consumers, intentional misuse with attributable diagnostics, boundary behavior and realistic allocation or copying evidence, with the maintainer judging the net reduction in defensive code. Adopt native C# facilities or interoperable existing tools where sufficient; narrowly targeted generation is justified only by a demonstrated gap. Do not recreate a broad discriminated-union ecosystem, force wrappers on every primitive, add core runtime dependencies or introduce a preview-runtime requirement. This goal supplies domain interoperability for decoding, changesets and domain programs, not their complete implementations, and cannot promise whole-program effect or exception safety.
