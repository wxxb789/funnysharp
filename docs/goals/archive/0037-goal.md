/goal
Advance FunnySharp's existing pure state machines into reusable business programs whose substate updates, message routing and output commands compose without duplicating routing glue or obscuring failure. Completion means an order workflow combines independently understandable inventory, payment and cancellation decisions, can lift a child program into a parent model, and can inspect or simulate emitted commands while using ordinary .NET code for real I/O. Existing OrElse and Replay remain starting capabilities, not new deliverables by themselves. A deterministic simulation must cover late responses, duplicate messages, stale request versions, rejected transitions and command failures, with explicit time, randomness and external replies where they affect decisions. Replay must not silently re-execute historical side effects; state or payload mutation must not invalidate claimed reproducibility. Command ordering, message correlation, state ownership and the distinction between expected domain rejection and execution failure must be visible. Completion evidence is a reusable program composition and deterministic scenarios compared with a direct switch-based implementation including its adapters, with complete consumer-code, state-copying and dispatch costs and maintainer judgment of readability. A small optional in-process execution adapter is permitted where it creates demonstrated value, but it must keep Task or ValueTask, CancellationToken and caller-owned dependencies at the boundary. This goal does not deliver durable event sourcing, distributed recovery, exactly-once effects, automatic transactions, a general actor runtime or a custom scheduler. Domain variants from 0030 may improve safety without becoming a mandatory replacement type system.
