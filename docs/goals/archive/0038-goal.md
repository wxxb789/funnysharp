/goal
Enable FunnySharp to process independent business entities concurrently while executing operations for the same key in the order observed from the input sequence, with explicit bounds on admitted work and buffering. Completion means an asynchronous account-event consumer can process different accounts concurrently while never starting a later admitted operation for one account before its predecessor has actually completed, and the consumer observes typed results and failures rather than losing them inside background work. Define key equality, null keys, result-order policy, hot-key behavior, fairness among admitted work, source backpressure and release of inactive key state. Large or unbounded key cardinality must not create unbounded retained queues or state outside the declared admission contract; any partition-induced blocking between different keys must be disclosed. Cancellation, source failure, callback failure, early consumer disposal and a non-cooperative callback must have honest cleanup semantics; do not promise BEAM-style forced task termination or global source ordering that the input does not provide. Completion evidence exposes per-key overlap, start and completion order, in-flight work and retained buffering under skewed inputs, and compares an equivalent BCL implementation and existing concurrency facilities with the full FunnySharp consumer. The maintainer judges whether correctness and consumer-code gains justify scheduling and allocation overhead. Reuse standard async streams, Tasks, cancellation and BCL coordination mechanisms, preserving the core runtime dependency policy. Do not add implicit retries, process supervision, distributed ownership, exactly-once delivery or a second general execution runtime.
