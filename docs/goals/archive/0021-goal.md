/goal
Make FunnySharp measurably friendly to coding agents and human developers through type-directed APIs, precise compiler feedback, and high-signal analyzers. Completion means a coding agent can discover one canonical way to express representative FunnySharp workflows from public signatures and documentation, common misuse is rejected by types or reported locally by diagnostics, and safe fixes are available where an automatic transformation is unambiguous. Analyzer coverage must address the material hazards established by the product contract, including invalid or uninitialized semantic carriers, silently discarded outcomes, deprecated or ambiguous API forms, and async, cancellation, enumeration, or resource patterns that can be diagnosed with acceptably low false-positive risk. Correct ordinary code must remain quiet, suppressions and severity behavior must be documented, and compiler tooling must add no runtime dependency to the core library. Evidence includes analyzer and code-fix tests, clean analysis of the repository's examples, diagnostic documentation, and a repeatable model-agnostic coding evaluation comparing idiomatic C# with FunnySharp across business outcomes, collections, async streams, concurrency, and ASP.NET Core. The evaluation must record compilation, semantic correctness, correction feedback, consumer-side LOC, API misuse, and maintainer readability judgment; a single curated prompt or one model run is insufficient evidence. AI friendliness must come from consistent types and feedback, not hidden prompt instructions or duplicate convenience APIs.
