/goal
Allow FunnySharp business code to compose typed data requirements while executing eligible reads in bounded batches, with fewer actual data-source calls than the equivalent per-item implementation and without losing result association, errors or request isolation. Completion means an executable order-enrichment consumer combines repeated customer keys, multiple sources and a dependent second stage; independent requests to a batch-capable source are grouped and deduplicated within an explicit execution scope, dependent requests wait for their inputs, and each result returns to the correct requesting position. A data source must explicitly supply its batch operation; ordinary HTTP or database calls must not be assumed to support batching. Missing records, per-key failures, whole-batch failures, exceptions and cancellation must have distinct documented handling, including incomplete or unexpected source responses. Equality, ordering, source parameters, tenant and authorization scope, cache lifetime and mutation invalidation must be explicit; there is no ambient cross-request cache. Admission, batch size and retained work must be bounded, and disposing or cancelling an execution must account for its started work without claiming forcible termination of arbitrary Tasks. Completion evidence includes a deterministic source that exposes requested batches and invocation counts, an equivalent hand-batched BCL implementation and an appropriate existing DataLoader comparison, with full consumer-code, latency and allocation trade-offs. The maintainer must be able to judge a material composability benefit beyond merely wrapping an existing loader. Preserve typed Result-style outcomes, ordinary asynchronous delegates and CancellationToken at the boundary, independent use outside GraphQL, and the existing zero-runtime-dependency core. Use or adapt an existing engine where it meets the outcome; a second DI container, general scheduler, write coalescing and implicit retries are outside this contract.
