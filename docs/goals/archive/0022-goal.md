/goal
Prove FunnySharp's business friendliness and composability in a realistic ASP.NET Core vertical slice that consumes produced packages only through their public APIs. Completion means the application demonstrates external-input validation, refined or already-validated domain values where appropriate, value-producing and no-value domain outcomes, asynchronous persistence or I/O, request cancellation, bounded parallel work, streaming where it is beneficial, pure state decisions with separately interpreted commands where relevant, and explicit HTTP error mapping. Minimal API results, ProblemDetails, typed results, and OpenAPI behavior must accurately reflect the possible outcomes without leaking HTTP types into the domain, swallowing unexpected exceptions, relying on global service location, or forcing domain code into a FunnySharp runtime. A maintainable idiomatic-C# comparison must make clear which ceremony FunnySharp removes and which semantics it adds; shorter code that hides cancellation, allocation, or failure modes does not count as an improvement. Evidence includes package-consumer build and test results, endpoint and OpenAPI integration tests, cancellation and failure-path tests, compiled examples, a call-site comparison reviewed by the maintainer, and relevant end-to-end allocation, throughput, or latency measurements. No compatibility with CSharpFunctionalExtensions, Funcky, or language-ext is required or permitted as acceptance evidence.
