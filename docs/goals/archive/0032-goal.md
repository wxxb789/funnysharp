/goal
Allow an application to reuse a fallible business check both in a fail-fast workflow that preserves its input value and in an accumulating validation of independent rules, without manually discarding unit payloads, reconstructing the original value or building unused tuples. Completion means a consumer can retain an order after a successful permission or inventory check and can apply an ordered set of independent checks to return that same order or all expected errors. The public meaning must remain distinct from Ensure's predicate check and Bind's value-changing composition; whether the final names are Check, CheckAll or another canonical form is not itself an acceptance condition. Empty rule sets, an already-failed input, repeated invocation, error order, lazy callbacks and callback failures must have explicit behavior. Dependent rules must not be evaluated as though independent, and accumulating validation must not acquire an inconsistent monadic Bind just to share syntax. Meaningful asynchronous checks must preserve cancellation and work with the supported Task and ValueTask conventions without multiplying equivalent receiver forms or blocking. Completion evidence compares the entire consumer with current Bind plus UnitResult.ToResult and existing Validation composition, proves that callbacks run only as promised, and discloses relevant allocation and delegate costs; the maintainer judges whether this represents an independent semantic operation rather than an alias. Keep existing carriers, BCL rule storage, caller-defined errors and the thin effect boundary. Schema introspection and domain construction belong to Goals 0026-0027; this outcome must also remain useful with ordinary existing business functions.
