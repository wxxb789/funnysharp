/goal
Let FunnySharp consumers state and enforce the cardinality assumptions of lookup and association code instead of silently collapsing missing, duplicate or ambiguous data into a convenient value. Completion means an order-to-customer enrichment consumer can require exactly one matching customer for each order, receive structured duplicate-key and missing-key failures, and preserve the declared source order and output-count relationship on success. Lookup paths must distinguish zero from multiple matches where that distinction matters, extending existing cardinality tools only when their current absence semantics lose required information. Define the supported key, comparer, null, duplicate and unmatched behavior, including whether uniqueness applies to the complete indexed input or only matched entries; a dictionary interface must not be claimed to reveal an opaque equality policy. Whole-operation success may require buffering, while streaming partial output must expose later failures honestly; neither shape may promise the other's guarantees. Completion evidence includes empty and repeated keys, unmatched rows, ambiguous matches, non-default equality, single enumeration and real failure locations, plus complete idiomatic C# and hand-indexed comparisons with index, output and error-storage costs. The maintainer judges whether the safer relation contract materially simplifies application code. Keep typed records and BCL collections, allow mutable inputs under a clearly stated lifetime contract, and prevent accidental Cartesian expansion without forbidding explicitly requested relations. No general SQL provider, ORM query translator, DataFrame universe or database-level integrity guarantee is required. Goal 0036 addresses nested shape transformation separately.
