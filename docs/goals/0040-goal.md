/goal
Determine whether explicit incremental computation is a useful and competitive optional FunnySharp capability for expensive, shared domain calculations that change locally over time. Completion is a maintainer-ready adopt, adapt, defer or reject decision grounded in an executable workload with shared dependencies and localized updates, comparing full recomputation, a reasonable hand-maintained incremental baseline and relevant .NET alternatives. Evidence must show the actual work avoided as well as graph maintenance, memory retention, update latency and setup costs; a trivial arithmetic graph or an assertion of spreadsheet-like behavior is insufficient. Establish an explicit consistency boundary for publishing a group of changes, input ownership and mutation rules, equality or cutoff behavior, error propagation, observer disposal and reuse isolation. Separate node-level recomputation from collection-level delta processing rather than claiming that placing a List in a node makes its operations incremental. State which dependencies are static or dynamic and how unsupported cycles or changes are handled; candidate assumptions about pure callbacks must be visible. The maintainer must be able to identify workloads where the mechanism pays for itself and workloads where ordinary functions remain preferable. BCL values, Result or Validation and caller-selected mutable or immutable storage must remain usable, with local mutation communicated through an honest change contract. Changesets from 0028 and reusable reductions from 0034 may supply useful inputs but are not mandatory implementation choices. This goal permits a focused prototype and explicit reconsideration of earlier caching exclusions, not an ambient cache, custom task scheduler, distributed reactive system or automatic I/O re-execution. A negative decision is valid completion of the investigation, not completion of a shipping incremental API.
