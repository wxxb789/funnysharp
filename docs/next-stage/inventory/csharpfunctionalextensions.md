### 4.5 F2 semantics summary (criteria-relevant)

- **Unsafe default state**: `default` is success; `Error` throws on success, `Value` throws on failure, so misuse is a runtime exception.
- **Implicit conversions choose branch direction silently** (`Result<string> = "text"` is success; the same-looking
  `Result = "text"` does not compile; `Result<int,int> = 5` does not compile). Branch construction is invisible at the call site.
- **Error type coupling**: `IResult<T> : IResult<T,string>` forces `string` errors into every non-generic constraint path.
- **Global mutable configuration** for separator, `ConfigureAwait` and `Try` error mapping.
- **Nullable annotations are partial**: `Maybe` and the HTTP file use `#nullable enable`; `Result`, `Result<T>`, `Result<T,E>`,
  `UnitResult<E>` do not (dump marks their members `nullability: Unknown`, vs `Nullable` on `Maybe<T>.Value`).
- **Error accumulation**: `Result.Combine(params Result[])` / `Combine(IEnumerable<Result>, string errorMessageSeparator)`
  join messages with `Configuration.ErrorMessagesSeparator` (default `", "`); `FirstFailureOrSuccess(params Result[])`
  returns the first failure. Arguments are evaluated eagerly by C# before the call.

## 8. F6 — async, streaming, concurrency

- Two parallel method universes (`Task` in `CSharpFunctionalExtensions`, `ValueTask` in `.ValueTasks`) × three operand
  classes (`LeftOperand` = async receiver, sync func; `RightOperand` = sync receiver, async func; `BothOperands` = async both).
  The naming describes C# extension-method dispatch, not user intent.
- `Configuration.DefaultConfigureAwait` (default `false`) is read by every async op via `DefaultAwait()`
  (`Result/Internal/TaskExtensions.cs#L16-L21`). `NullableExtensions.ToResultAsync` hard-codes `ConfigureAwait(false)`
  instead (`Result/NullableExtensions.cs#L26-L31`), which is inconsistent.
- No `Task.Run` anywhere in the library (grep of the pinned snapshot).
- No `CancellationToken` parameter in any `Result` operator. Only `MaybeExtensions.Match` (16 token overloads) and the
  HTTP extensions accept tokens.
- `Combine` uses `Task.WhenAll` (unbounded concurrent fan-out, no degree limit, no token); `CombineInOrder` awaits sequentially.
  The `ValueTask` overloads first call `tasks.Select(x => x.AsTask())`, converting every `ValueTask` to a `Task`
  (`Result/Methods/Extensions/Combine.ValueTask.cs#L13-L32`), so the ValueTask variants allocate like Task ones and
  remove any single-consumption discipline.
- No `IAsyncEnumerable`, `Channel`, `TimeProvider`, `Parallel.ForEachAsync`, `Task.WhenAny`-based first-success.
- `ValueTask` methods follow the same reactive shape (no single-consumption guard); dumps show no `ValueTask` overload that
  buffers or converts to `Task`.

## 9. F7 — effects, resources, environment

`WithTransactionScope`/`BindWithTransactionScope`/`MapWithTransactionScope` (49 public members across the sync and
`ValueTasks` namespaces; the `WithTransactionScope` helper itself is private) create an
ambient `System.Transactions.TransactionScope` around the supplied delegate (e.g. `Result/Methods/Extensions/WithTransactionScope.cs#L14-L70`).
No retry, timeout, `TimeProvider`, DI, environment, resource-scope or cancellation-policy capability exists in the package.
`Try` is the only exception boundary and it is unbounded (F2.3).

## 14. Representative call sites (pinned) and semantic-LOC counts

Counting rule used here (operationalises criterion 2): count each expression/statement that carries workflow meaning —
invocation with observable effect, pipeline operator, branch/guard, recovery/observation step, or value-shaping
conversion whose failure semantics matter. Do **not** count argument construction (error strings, DTO literals),
`new` of domain objects, formatting, braces, or `using` directives. A lambda contributes 1 for its invocation plus 1 per
meaning-bearing statement in its body. These counts are analyst judgment; snippets are quoted so the lead can recount.

**CS1 — README "Compose multiple operations in a single chain"**, `README.md#L56-L64` (URL pinned at `e0fc908`):

```csharp
return _customerRepository.GetById(id)                        // 1 producer
    .ToResult("Customer with such Id is not found: " + id)    // 1
    .Ensure(customer => customer.CanBePromoted(), "...")      // 2  (op + predicate call)
    .Tap(customer => customer.Promote())                      // 2  (op + body)
    .Tap(customer => _emailGateway.SendPromotionNotification(customer.PrimaryEmail, customer.Status)) // 2 (op + body; returned Result discarded)
    .Finally(result => result.IsSuccess ? Ok() : Error(result.Error)); // 2 (op + branch)
```
CFE total: **10**. Plain C# equivalent (same operations, `Maybe`-returning repository):
`var maybe = ...` (1); `if (maybe.HasNoValue) return Error(...)` (2); `var customer = maybe.Value` (1);
`if (!customer.CanBePromoted()) return Error(...)` (2); `customer.Promote()` (1);
`var notify = _emailGateway.SendPromotionNotification(...)` (1); `if (notify.IsFailure) return Error(notify.Error)` (2);
`return Ok()` (1) — **11**. Net change −1 semantic LOC; the chain also hides that
`Tap` ignores `SendPromotionNotification`'s `Result` (silent failure path in both CFE and `Tap`-shaped code).

**CS2 — async middle-of-chain**, `CSharpFunctionalExtensions.Examples/ResultExtensions/AsyncUsageExamples.cs#L19-L28`:

```csharp
return await GetByIdAsync(id)                                          // 1
    .ToResult(...).Ensure(...).Tap(c => c.PromoteAsync())              // 4 (3 ops + predicate body)
    .Bind(c => gateway.SendPromotionNotificationAsync(c.Email))        // 1
    .Finally(r => r.IsSuccess ? "Ok" : r.Error);                       // 2
```
CFE total: **8**. Plain async equivalent: `await GetByIdAsync` (1), null branch (2), guard branch (2), promote await (1),
notify await + branch (2+2), return (1) = **11**. Net −3, mostly error plumbing.

**CS3 — LINQ query syntax over validation factories**, `README.md#L621-L626` vs `#L647-L655`:

```csharp
var customer =
    from name in CustomerName.Create("jsmith")        // 1 call + 1 bind
    from email in Email.Create("jsmith@example.com")  // 1 call + 1 bind
    select new Customer(name, email);                 // 1 select
```
CFE total: **5**. Plain: two factory calls (2) + two `if (IsFailure) return Error` guards (4) + construction (1) = **7**.
Net −2 per two validations, scaling with the number of binds. The async form needs `await (from ... select ...)`.

**CS4 — validation aggregation**, `README.md#L35-L45`: CFE `Combine(name, email)` + `if (result.IsFailure) return Error(result.Error)`
= **3**; plain three guards = **6**. Net −3, scaling linearly, at the cost of a single comma-joined error message
(no per-input location; separator is global configuration).

**CS5 — collection/dictionary absence**, `README.md#L405-L434`: `fruits.TryFirst(predicate)` = **2** (call + predicate) vs
`fruits.FirstOrDefault(predicate)` = 1 but with value-type default ambiguity; `fruitInventory.TryFind(key)` = **1** vs
`TryGetValue` + branch = **3**. The gain is type-safety of absence (criterion 4), not raw count.

**CS6 — upstream tests as call sites.** Tests exercise the same surface and are useful evidence of intended usage:
`MaybeTests/Extensions/ChooseTests.cs#L10-L21` builds `new[] { Maybe<int>.None, 1, Maybe<int>.None, 2, 3 }` via implicit
`int → Maybe<int>` conversions and asserts `source.Choose(x => x * 2)` — the implicit conversion is relied on as a
feature, which is exactly the AI-predictability risk when it is absent from the reflection surface.
`ResultTests/AmbiguityTests.cs#L16-L27` exists solely to assert that `result.Bind(async _ => await GetTask())` and
`Result.Try(async () => ...)` compile "without raising ambiguity errors" — the library ships a regression test for its own
overload ambiguity, confirming criterion 3/5 as a live problem rather than a theoretical one.
